# Firebase emulator adapter

This workspace exposes the narrow Officer/Protection backend slice through second-generation HTTP functions. `firebase.json` binds Auth, Firestore and Functions emulators to loopback; `.firebaserc` selects the resource-free `demo-mothership` project. Run the repository's pinned emulator test command from the root. Cloud deployment and actual Cloud Tasks delivery are outside this slice's evidence.

All four functions accept `POST` with JSON, a maximum 2,048-byte body, and `Authorization: Bearer <Firebase Auth ID token>`. Command/receipt/advance bodies use the shared protocol-1 schemas. `serverTime` accepts exactly `{ "protocolVersion": 1, "matchId": "<admitted-match-id>" }`; membership is required. Responses set `Cache-Control: no-store, private` and contain safe contract errors without exception details. Clients cannot select their actor identity.

Production requests also require `X-Firebase-AppCheck`, verified by Admin SDK. The only bypass requires all of: `FUNCTIONS_EMULATOR=true`, a `demo-*` project, and loopback Auth plus Firestore emulator hosts. Local tests exercise this branch and test the production verification guard with an injected verifier. These checks do not establish production App Check attestation or mobile-device acceptance.

Security Rules admit only the member's composed player view and the shared public view. Display membership can read public facts but no player's private document. Membership, engine, private events, receipts and scheduling outbox are inaccessible to clients; generated documents deny every client write. The API independently authorizes Admin SDK operations, which bypass Security Rules.

Presentation events live in `matches/{matchId}/audienceEvents/{audienceKey}/items/`. The public key is `public`; a player's private key is the verified UID. Queries must constrain `audience.kind` to `public` or `player`; private queries also constrain `audience.seatId` to the member's seat. The event's revision belongs only to that audience. There is no shared private sequence exposed by document IDs. Read retained events only as presentation history; replayed animation cannot determine gameplay.

`test/helpers.mjs` creates identities through the real Auth emulator REST endpoint, refreshes the same identity, invokes the four player-facing functions, and makes token-authenticated Firestore REST requests. It refuses non-loopback hosts and projects other than `demo-mothership`. Fixtures and seeding stay in test harnesses; no seed, vote bypass or resolution HTTP endpoint is exported. The helper cannot invoke the private task function.

`src/tasks.ts` provides a lazy Admin SDK Cloud Tasks enqueuer for a reviewed worker name. It passes only the match/phase/deadline-token envelope, uses the outbox's stable hashed task ID and absolute deadline, and acknowledges `ALREADY_EXISTS` after a lost enqueue acknowledgement. Other failures remain pending for repair. The `deadlineTask` second-generation task export is configured with `invoker: private` and validates that exact envelope before calling the core. Stale/duplicate jobs acknowledge safely; unavailable evaluation throws a safe error for retry. Unsupported pinned versions also fail, with at most five configured attempts, and require operator compatibility review rather than automatic rule migration.

IAM is the production task authentication boundary. Task request metadata is not an independent identity proof, and the task callback must never be routed through an untrusted player HTTP endpoint. Functions emulation does not enforce production IAM. Unit tests inject a queue and service; no actual Cloud Tasks call, task delivery or IAM policy has been tested here. An authorized service-account invoker and repair runner must be reviewed before connecting the adapter in staging. The enqueuer's function resource is `locations/us-central1/functions/deadlineTask` for the current candidate region.

Implementation references: [HTTP functions](https://firebase.google.com/docs/functions/http-events), [Auth token verification](https://firebase.google.com/docs/auth/admin/verify-id-tokens), [custom-backend App Check verification](https://firebase.google.com/docs/app-check/custom-resource-backend), [Auth emulator](https://firebase.google.com/docs/emulator-suite/connect_auth), and [Firestore Rules](https://firebase.google.com/docs/firestore/security/rules-conditions).
