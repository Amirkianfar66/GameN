# Character restyle phone performance budget

7 November 2026. Frontend accepts Integration's proposed frame, input and critical-asset targets below. First usable paint, memory, regression margins and the device list are Frontend counterproposals awaiting Integration agreement. **Every number is a target, not a measured result.** This budget is for adoption from DSN-REQ-17, not the dev-only character prototype.

The [production architecture](../architecture/production-v1.0.md#11-quality-targets-and-release-tests) already proposes 60 fps on agreed midrange phones, 30 fps with lower effects, local response within 100 ms and 6 MB of initial compressed critical assets. Its separate network acknowledgement/state-delivery targets are not renderer latency measurements.

## Proposed limits

MB means 1,000,000 bytes for transfer. MiB means 1,048,576 bytes for memory. Both absolute limits and regression limits apply; meeting one does not waive the other. All startup limits below use the fixed network and authenticated-resume scenario defined in the protocol.

| Metric | Normal iPhone / midrange Android | Lower-effects low-end Android | Agreement status |
| --- | --- | --- | --- |
| Critical transferred assets | ≤6,000,000 compressed response-body bytes, including app code, CSS, fonts, required board art, nine crew and portraits | Same ceiling | Accept Integration/architecture target; decimal unit is this proposal's clarification. |
| Active-animation frame time, p95 | ≤16.7 ms; 60 fps target | ≤33.3 ms; 30 fps target | Accept Integration target. Trace total frame work and delivered cadence, as defined below. |
| Local selection/target feedback, p95 | ≤100 ms from input to painted selection state | ≤100 ms | Accept Integration target. Server acknowledgement is separate. |
| First usable paint, cold, p95 | ≤4.0 s | ≤6.0 s | New Frontend proposal. |
| First usable paint, warm, p95 | ≤1.5 s | ≤2.0 s | New Frontend proposal. |
| Settled live JavaScript heap after nine-crew warm-up | ≤48 MiB absolute; ≤8 MiB added over matched baseline | ≤40 MiB absolute; ≤8 MiB added | New Frontend proposal. |
| Attributable WebContent/renderer resident footprint, peak | ≤200 MiB absolute; ≤32 MiB added over matched baseline | ≤160 MiB absolute; ≤24 MiB added | New Frontend proposal. Includes non-JS cost where tools expose it; missing instrumentation is unmeasured. |
| Settled memory growth, minute 5 to minute 30 in the same state | ≤5 MiB **and** ≤10% of minute-5 memory, independently for heap and attributable process footprint | Same rule | New Frontend proposal; warmed caches must plateau. |
| Frame regression against matched baseline | Candidate p95 ≤baseline p95 + max(0.5 ms, 5% of baseline p95), while still meeting the absolute limit | Same rule | New Frontend proposal; small margin avoids treating trace noise as unlimited regression. |
| Startup regression | Candidate p95 ≤baseline p95 + max(100 ms, 10% of baseline p95), while meeting the absolute limit | Same rule | New Frontend proposal. |
| Local-input regression | Candidate p95 ≤baseline p95 + max(5 ms, 10% of baseline p95), while meeting the absolute 100 ms limit | Same rule | New Frontend proposal. |
| Lifecycle stability | Zero crashes, tab reloads from memory pressure, retained unmounted character trees or growing animation/listener counts after repeated settle/dispose cycles | Same rule | New Frontend proposal. Record interruptions rather than dropping failed runs. |

Memory ceilings are product proposals, not browser/vendor guarantees. No baseline memory result exists in this task. If the unchanged app already exceeds an absolute ceiling, record it and resolve the budget with Integration before acceptance; do not silently relax it or report the candidate as passing. Lower effects retains the approved character geometry, colors, meaningful poses and privacy. Reduced motion is an independent preference and also needs coverage.

At 60 Hz, browser overhead shares the 16.7 ms frame; target roughly 10 ms for application-controlled rendering work to leave room for the browser. This explains the head-cache requirement but is not a measured GameN result. The 100 ms selection target is this app's local response target, not an INP claim. ## Metric definitions

**First usable paint (custom app metric, not FCP or LCP):** navigation start to the first presented frame containing the authorized screen, readable names/status/timer, the correct crew/portraits and the controls currently offered by the snapshot, with event handlers attached and required art decoded. Verify usability with the first permitted interaction. A skeleton, blank board, button with no handler, or artwork from the wrong selected release is not completion. Measure setup selection and an existing nine-crew match independently; both must pass. Deliberate phase waits, such as the existing selection/reading minimum, are not changed to obtain a measurement.

Use an already authenticated test account with valid saved match/seat context. Cold clears the HTTP/art/code cache while retaining the fixed auth test setup; record service-worker/cache status. Warm preserves that same successful cached build and reloads the same state. Separately report navigation-to-snapshot arrival and snapshot-to-usable-paint; end-to-end time includes the actual backend/session delivery, asset fetch/decode, template creation and mount. Do not subtract slow work from the acceptance result. A service failure or expired auth is a labeled failed/resume case, never an omitted sample. Fresh sign-in is a separate user-flow check.

**Frame time:** total browser frame-processing work (JS, style, layout, paint and available composition work) during continuous visible animation. Use at least 30-second active windows per scenario, preserving GC and long frames; do not dilute p95 with static/hidden/idle samples. Also report delivered-frame intervals, missed deadlines, FPS and trace gaps. At least 95% of intended frame deadlines must be met; a 60 Hz `requestAnimationFrame` callback that presents stale content is not proof of 60 fps. Lower effects measures actual new frames at its intended 30 fps cadence. Record refresh rate; do not infer workload time from callback spacing alone. Safari's frame timeline separates script/layout/paint work; save the raw recording. [WebKit Timelines](https://webkit.org/web-inspector/timelines-tab/)

**Local feedback:** input event timestamp to the first presented selected/targeted state for that input, including handler work and paint. Measure at least 100 valid local selections/targets per sustained run. Record server-result latency separately and preserve pending/disabled behavior. A full-frame screen recording is useful for visual corroboration but is not sufficiently precise by itself for a 16.7 ms claim.

**Memory:** report JavaScript live heap and attributable tab/WebContent/renderer memory separately with the exact tool/counter/unit. JS heap omits native DOM, decoded image, GPU and other process costs. Use Android remote Chrome traces/heap snapshots plus available OS process accounting, and iPhone Safari Web Inspector plus available WebContent process accounting. Do not relabel Safari inspector memory as resident footprint or use unavailable Chromium-only APIs as iPhone evidence. If total process accounting cannot be obtained, mark that gate unmeasured and resolve the instrumentation with Integration. Chrome documents the distinction between JS memory and process footprint and the use of heap snapshots to find retained detached elements. [Chrome memory diagnostics](https://developer.chrome.com/docs/devtools/memory-problems)

## Repeatable paired-baseline protocol

1. **Pin both builds.** Record baseline and candidate git SHA, DSN-REQ-17 source commit and hashes, art manifest/version, token hash/version, runtime catalog digest, build command/mode and server target. The baseline is the unchanged approved runtime at the same gameplay tuple and scenario. Build production assets, not a dev server or prototype review page. Add a machine-readable result record with `target`, `observed`, `status` and artifact path; use `unmeasured` rather than zero for absent results. Routine records contain no private-role payloads or device serial numbers.
2. **Control the device and environment.** Name the real model/variant, RAM, OS/browser build, viewport/DPR, refresh rate, battery/low-power mode and thermal condition. Use fixed brightness, no unrelated foreground activity, same connection and a stable 20 Mbps down / 5 Mbps up / 80 ms RTT profile applied at the router/proxy for both browsers. Record the actual shaping tool and observed throughput/RTT. Keep CPU unthrottled on the physical device. Alternate baseline/candidate order and allow the device to cool between pairs. Do not compare a cooled baseline with a hot candidate.
3. **Measure startup.** Run 20 cold and 20 warm samples per build/device for setup and nine-crew match resume. Reset only the stated caches/auth context. Record first usable paint, snapshot arrival, required asset bytes, decode/mount spans and first input. Include all failed attempts with their reasons. Use nearest-rank p95, retain individual samples and publish the count; never report only the fastest run. Split every result by device, mode and scenario rather than pooling away a slow device.
4. **Exercise nine-crew pressure.** All nine must be visible on the board and in selector/list scenarios, including Rigel's beard and Vega's curls. Exercise front/down/back, crew/gown/prison, injured/eliminated, body/front prop layers, the same character concurrently in capsule and board, film mounts and portraits. Include steady board idle/blinks/hair, walks and gesture blends, capsule entry/talk/exit, rescue/release/eject/clone, ability chips and list scrolling. Use existing authorized/synthetic review fixtures; never create an impossible gameplay state to claim an end-to-end match result. Keep snapshot slots and phase timers unchanged.
5. **Run sustained sessions.** Three 30-minute foreground runs per build/device/mode with a repeatable one-minute cycle: board → permitted local target → cancel/settle → crew list/selection fixture → board motion/capsule/film fixture → settle. Record whether each step is a real authorized flow or presentation fixture. Collect at least 30-second active frame windows at the start, middle and end for each motion scenario. Take comparable settled memory samples at 1, 5, 15 and 30 minutes after returning to the same nine-crew board. Five minutes is the cache warm-up comparison point. The final five-minute median frame p95 must also stay within the same absolute/regression limits as the first measured window. Mark thermal degradation; do not trim it out.
6. **Separate profiling from acceptance traces.** Run clean timing passes without heap-snapshot/allocation tooling or screen recording; use separate paired diagnostic passes for memory, DOM/node/listener counts and video. Record inspector attachment and tracing overhead. If a diagnostic snapshot forces GC, use the same sequence on both builds and label it; never force GC to make ordinary frame/startup results pass. Check mount/dispose cycles for retained nodes, cache entries and animation handles. The head geometry/template build count must plateau; per-frame heavy head serialization or full SVG remount fails the rendering strategy even if a desktop run appears fast.
7. **Cover preferences and lifecycle.** Normal and reduced motion on iPhone/midrange; lower effects with both preferences on low-end Android. Switch reduced motion while mounted: meaningful gesture poses persist and idle/hair drift stops. Exercise background/foreground, orientation/resize, snapshot updates, refresh/reconnect and art-load failure. Capture interrupted-run behavior separately; it must not replay a finished film, hide the playable figure or change an authoritative phase's duration. A hidden tab is excluded only from foreground frame distributions, with the interruption explicitly retained in the log.
8. **Apply every gate.** Report per-scenario p50/p95/max, failed/total startup attempts, critical bytes, frame counts/deadline misses, memory absolute/delta/growth, lifecycle results and baseline differences. Repeat only when a change, failed run or unresolved concern justifies it. A missing phone, missing trace counter or missing release pin leaves its result unmeasured; desktop screenshots cannot turn it green. Integration must agree the remaining proposal rows and sign off the results before adoption merge.
