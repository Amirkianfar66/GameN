# Owner decision: pass an ordinary turn

Issue [#85](https://github.com/Amirkianfar66/GameN/issues/85), recorded 8 October 2026 from deployed base `90f079d113e014a0cc0d3a337ae69b020abe1ce7` (PR #84). The game owner requested an explicit Pass control that finishes the active player's ordinary turn early. The confirmed immutable rule overlay is [ordinary-turn-pass-owner-decision-2026-10-08.json](../../rules/overlays/ordinary-turn-pass-owner-decision-2026-10-08.json).

## Authorized behavior

Only the active non-eliminated player in `ORDINARY_TURN` may submit strict protocol-2 `{ "type": "PASS_TURN" }` while trusted `startedAt <= now < endsAt`. Injured and jailed players retain their speaking-turn right. Registered actions and shots stay queued for canonical resolution; Pass spends no extra resource and does not resolve or cancel them.

A pending Hack follows the passed ordinary turn for a fresh full 60-second window. Otherwise the recorded order advances to the next living player, or to the normal post-turn release-choice/Jail-vote phase. Hack, election/runoff, release choice/vote, Jail vote and showdown cannot be passed or closed early. Bots do not automatically pass. All remaining gameplay and disclosure rules are inherited from the exact parent ruleset.

The server hints eligibility through the existing `legalTargets.PASS_TURN = [self seat ID]`. The strict view shape does not expand. This hint is role-independent and is absent in legacy matches; server authorization remains authoritative.

## Immutable version and compatibility policy

New gameplay tuple:

- Protocol `2`.
- Engine `full-game-1.1.0`.
- Ruleset `in-person-v1-pass-2026-10-08`.
- Ruleset hash `a25cec290370a3140829292b3cb8bdda3fb4402e0b529b56c6ef9692f7870183`, the SHA-256 of the exact immutable overlay bytes.

The reviewed legacy tuple remains supported: protocol `2`, engine `full-game-1.0.1`, ruleset `in-person-v1-2026-10-06`, hash `6ca355ebf3553e24a16eae847f5b550b1d3da8bd0a2daf80f69ec94dd2809a90`. Tuples cannot be mixed; unknown engines/hashes are not admitted. This does not expand service support to `full-game-1.0.0`.

A new match records its tuple in server-only `engine/gameplayPins` at creation. An existing match without that document uses the exact legacy tuple, including before Begin or before the private deal. Existing prepared deals and running states keep their recorded versions. Deal creation copies the creation pin; launch and journal replay pass recorded versions into the engine constructor. Existing asset pins and receipts are not rewritten. No old match acquires Pass after deployment or reconnect. The host-readable `control/session` retains its existing keys; version pins do not require a host-reader schema change.

The earlier random-room decision remains an admission policy override; historical rule/source files and source lock are preserved. Staged setup stays `staged-start-1`, with 30-second character selection and at least 30-second reading plus every human Ready. The client must obtain Pass capability from current server views and use the normal command IDs, receipt reconciliation and single outstanding-command flow.
