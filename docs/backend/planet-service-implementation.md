## Behavior and authority

The production factory binds the actual pure engine, protocol 3 / `planet-game-1.1.0` / `in-person-planet-private-feedback-2026-11-06`, source hash `4a1fc0e0dc21255253e31ae46e6042f9bd71e3fdec0f82f8a79b3ce213d01bfa`. No gameplay, duration, ruleset/hash, authority source or historical manifest changes are included. The service response additions are requester-bound `admission` and typed recovery `{matchId, seatId}`; see [the admission contract](planet-service-admission-contract.md). Frontend adoption requires its affected-role review.

- Host approves player/display admission, sets practice bots, begins setup, issues recovery and aborts. Public `advance` and `runBots` operations are host-only service controls; server-private workers provide automatic advancement and bot execution. Players issue only their own legal commands, character choices and Ready. Displays receive public/session data after approval and cannot act as a player.
- Character choice lasts 30000ms. Unclaimed characters, shuffled roles, capacity-respecting independent A/B placement and initial turn order are prepared once. Reading lasts at least 30000ms and every human must also confirm Ready. Delayed tasks start a fresh full subsequent window. Reading/reload/retry never redeals. All-bot matches use the same windows.
- An authenticated read composes only the caller's permitted audience. Pending/closed requests have no roster, setup, board, role, private view or host admission list. Current API does not implement declining; the explicit denied schema standing is reserved. No UID comes from a request body. The original admission request ID must survive retry/reload.
- Recovery codes are server-generated, hashed in authority keys, expire after fifteen minutes and are single-use with a seat binding revision. Successful recovery revokes the old UID's member, requester and display access and transfers a host-owned seat's host capability to the new UID. It returns the requested match and assigned seat. Actor-scoped command receipts follow the seat; the revoked identity cannot retrieve them.
- Command receipt lookup and fingerprint conflict detection precede phase validation. Accepted and rejected engine receipts persist atomically with state, journal and outbox. A lost acknowledgement is reconciled by `receipt` or exact command retry; changed content with the same actor/command ID is rejected. The service consumes an authenticated caller's fixed 120-request/minute budget even when the semantic operation fails; invalid/authless preflight reaches no persistence.

Existing `members[].seatId`/`characterId` and engine board seat/slot fields retain character identity and logical placement across reload/recovery. No shared character-placement field, inferred Supply marker, new animation authority or extra game event is introduced.

## Persistence, replay and liveness

`createFirestorePlanetStore` buffers writes until all authority reads finish, then commits JSON chunks, digest metadata, receipts, journal and outbox together. Nested drawing arrays round-trip without Firestore nested-array loss. Corrupt digests/envelopes and cross-match/tuple state are rejected. Budgets are explicit (48KiB chunks, at most 80 chunks per value, at most 450 writes and 6MiB raw JSON per transaction); accepted state is never truncated. Collections are server-only under the existing catch-all rule.

The saved full tuple and artwork identity are validated, independently of the new-creation configuration. Preparation stores its explicit tuple. Historical Planet 1.0.0 and 1.0.1 sessions continue through their saved behavior and omit successor-only fields. Legacy protocol 2 service dispatch remains separate.

Every match journal has a transactionally assigned contiguous sequence. `PREPARE` records the deal and random inputs; `INITIALIZE` records the actual game creation. Engine `COMMAND` records actor/request/context/receipt; `DEADLINE` records the exact expected phase/token and random inputs. `OPERATION` with `abort` records the authoritative abort context. Replay uses these recorded contexts and explicit setup versions, never today's creation defaults. Administrative operations are separate from engine commands and carry no recovery code in the journal.

Random samples/identities are generated once outside transaction retries. Each bot sees only its own engine projection and uses a simple practice policy, without social-balance claims. Bot transitions have unique identities and domain-separated random streams derived from the recorded secure seed; each exact engine input is journaled. Work is bounded to 32 accepted commands per batch. Unchanged bot passes do not rewrite the session, preventing trigger loops.

Timers use `planetDeadlineAt`, including Blackout's five-second boundary. A phase/token's outbox record is created once and retains dispatch/completion state across private commands. Private Tasks, Firestore dispatch/bot triggers and one-minute repair supply liveness; duplicates and stale work do not repeat a transition. Repair handles lost/overdue tasks directly and backs off failed entries so they cannot indefinitely occupy the first page. A reading deadline with missing human Ready completes without starting; the subsequent Ready operation starts the already prepared game when the minimum time has elapsed.

P27 retains exactly six seconds after actual Sync and opens a fresh full sixty-second Jail vote after delayed processing. P28's early Officer choice preserves phase, timestamps, other audience packets and deadline metadata update time. Authority metadata is never a client subscription; HTTP reads contain no journal sequence, Firestore timestamp, world key or hidden action count.
