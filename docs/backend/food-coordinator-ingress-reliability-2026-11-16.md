## Local causal trace

With the original owner FIFO and the same seven-player, two-operator script, trial 03 reproduced a 10.056-second heartbeat and stale-owner responses. The first competing writer was owner renewal. Renewal read the owner record, prepared writes for it, and entered commit. The first heartbeat in the FIFO had already read that record's metadata and began the fragment read while renewal was committing against the same key. Renewal's commit returned code 10 after 2,019.8 ms. The heartbeat's fragment read returned code 3 after 8,842.6 ms. Its retry ultimately returned `STALE_OWNER`. The complete heartbeat storage operation held the FIFO for 10,044.1 ms. The next heartbeat received the same stale-owner refusal after waiting behind it. Trial 01 exposed the same overlap with a 2,003.4 ms fragment read and a 2,043 ms worst heartbeat. Trial 02 completed without a multi-second span.

The trace marks SDK reads, writes, commits, attempts and settlement under each operation. Hashes identify the same local records without exposing UIDs, commands or document contents. The reader takes metadata and then fragments in the same transaction. Firebase documents that the emulator can hold locks for concurrent writes longer than production and can differ in transaction behavior. These observations establish the local renewal/append collision. Hosted attribution requires a bounded synthetic run through reviewed deployed routing. [Firestore emulator transaction limitations](https://firebase.google.com/docs/emulator-suite/connect_firestore#transactions).

## Correction

The owner-routed variant now puts ownership acquisition and renewal on its existing per-Task durable append FIFO. Both modes keep the same epoch checks, lease duration, admission records, timestamps, game rules, and receipt lookup. The owner driver already sequences its own apply and renewal. Gameplay apply remains outside the append FIFO, so the contact path can admit while an apply is paused. Lease renewal still uses Firestore and can fail closed. Actual successful append time remains the authoritative contact or press time. The old owner and unknown-outcome tests exercise takeover and duplicate recovery.

The observed span spent seconds on a shared locked record while an overlapping writer was committing. The generic representation adds a metadata read and fragment read for this record. A compact representation could lower SDK calls and bytes, and the competing owner read and write would still need coordination. This correction keeps the current encoding and measures transaction scheduling directly. Any future encoding comparison needs equivalent byte budgets, fencing and unknown-commit recovery.

The prototype also associates own-command publication telemetry with the original seat binding revision. Frames suppress the witness for missing or changed binding revisions. The wire and production capability registry are unchanged. Use `admissionMode: 'owner-fifo'` in the dev browser launcher to exercise this correction. The existing launcher defaults to the shared cursor unless it sets the mode explicitly.

### Routing choice for review

| Option | Services and constraints |
| --- | --- |
| Direct addressing | The current API has multiple replicas and provides no per-instance address. This option requires a separately addressable private worker tier with a trusted endpoint registry and explicit placement per Task. An API replica reads the current destination and epoch, forwards the authenticated input and rechecks on a stale route. It leaves arrival timestamps at the durable append. It saves an inbox write and watcher hop. Affinity or a service-wide instance limit alone cannot stand in for a verified route to the leased process, especially during rollout and failover. |
| Immutable private inbox | The existing scalable API persists authenticated intents under separate keys and returns the canonical original receipt when ready. A bounded private worker can reuse the existing task-handler deployment if its runtime and routing limits support the owner loop. A reviewed outbox wake starts that loop after JOIN, and a leased worker reads or watches the inbox and uses the corrected FIFO for durable ordered admission. Snapshots and audience-scoped delivery can run on any replica. This adds a write and a watcher hop, with no direct API-to-instance route. |

I recommend reviewing the inbox seam first. It keeps existing API scaling and removes the owner-addressing dependency. An inbox acknowledgment proves durable intake only. The owner must still claim authority, revalidate the binding and Task at append, and assign the actual successful append time. Keep an original command fingerprint for deduplication. The API can await its original durable receipt or report an unknown outcome through the reviewed client path. Hold UP uses its own send and exact original binding without waiting for DOWN's response.

Specify intake ordering in the implementation review. A possible design uses a strongly consistent inbox query ordered by server-assigned intake commit timestamp and a stable tie key. A durable scan watermark must account for the entire tie group before advancing. The ordered admission stream stays authoritative, and rows already admitted behind JOIN drain before any new inbox row. The owner advances its consumption cursor together with admitted work, or can retry from the immutable inbox after a crash. A new host service becomes necessary if the existing private task handler cannot reliably maintain the bounded owner loop and wake recovery. Neither option should change the 2-second presence or 8-second lease/grace settings. A hosted seven-player synthetic test must measure actual durable admission, receipt recovery, owner renewal, and the extra hop before committing to a broader rollout.

## Implemented private inbox

The implementation starts at `529e2412ed3d5cd45a31cab0f5489519a3807184`. The measured Backend source is `6f4ce31e5ac6c32dc8dbe863355f927bcfb91ddb`. Existing matches follow their saved profile. New creation can explicitly select `food-owner-inbox-1`. A missing profile uses the existing authority path and an unknown saved profile fails closed. Engine, ruleset, art pins, common return time and recorded gameplay event semantics are unchanged. The shared stream contract comes from Integration's `27de988c3334cbe57d42cc68f1ef2ceb6cdd67c7`.

JOIN atomically records the private route and the full existing admitted prefix. The private owner drains that prefix with each entry's original clock before admitting inbox intents. Intake records an immutable request and scope-bound actor revision. Firestore orders committed visible pending rows by server request timestamp and stable hashed intent ID. Atomic removal and consumption avoid a global time watermark. A later visible row waits for the next selection. The actual durable append supplies the authoritative clock, and the exact saved response handles duplicate requests and uncertain replies. A known stale binding or semantic refusal consumes the row with a durable refusal. Transient or ambiguous writes retain the existing recovery path.

The bounded worker remains on the independent Firestore listener until closure or its 45-second budget. It renews through the same serial execution path and records a durable watchdog with each renewal. An independent generation gate makes an intake write emit a fallback wake if ownership changed before it committed. Acquisition validates the immutable wake in a read-only transaction before claiming ownership, allowing the dispatcher to acknowledge the enqueue concurrently. Return or abort closes the scope in the same transaction as the parent state, result marker, journal and next ordinary wake. The stream offer exposes the public Food step. Each projection checks audience authorization and reports participant freshness against owner, presence and due boundaries. The existing Firestore default deny covers the inbox collections.

### Changes to evaluate after the browser repeat

1. **One authorized API snapshot for timed inputs.** Merge the classification and authorization reads for human `TASK_PRESS` and explicit heartbeats on the opted-in profile. In the same read-only callback, classify the stored Session, run the existing validated load against that transaction's cached envelope, resolve the open route, authorize the caller and capture the binding and current listener. Feed that capture to the existing intake path. The intake write transaction still checks the current scope, binding generation and listener generation. A changed scope or binding follows the existing retry path. Invitation commands, private receipt lookup, setup, legacy matches and host recovery keep their existing entry points.

2. **Skip the separate worker probe after a known drained commit.** A live worker can carry a hint from a confirmed processing commit that the prefix was drained. When a pending intent is available, attempt its ordered append on the same owner lane. In that append transaction, recheck the scoped route is open, the exact owner ID and epoch still hold, the lease is valid, and durable Control satisfies both `processedSequence >= cutoverThrough` and `processedSequence === nextSequence - 1`. A pending prefix causes an immediate fallback to the existing drain and a fresh pending-head selection without consuming the cached candidate. A closed scope, stale owner, missing Control or uncertain prior commit uses the existing recovery path. The chosen timestamp still comes from the successful append, with ordinary due boundaries and receipt deduplication retained.

Validate both changes with the existing concurrent JOIN, exact retry, binding recovery, ownership takeover, abort and common-return cases. Record bounded redacted spans for request receipt and auth, intake commit, pending-head notification and selection, ordered-append read groups, authoritative stamp and commit. Compare the same network conditions and report misses with successful samples. The report makes no claim about a warm Session cache or per-key RPC latency.
