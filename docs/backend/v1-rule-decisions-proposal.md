## Approved decisions

| ID | Approved complete-V1 behavior | Original source gap |
| --- | --- | --- |
| V1-01 | Before roles are dealt, each player chooses Room A or Room B. Roles are randomized independently; room choice has no role restriction. | Initial room assignment is provisional (D01). |
| V1-02 | A healed player returns to their last A/B room at end-round finalization. A released Healthy player returns there; a released Injured player goes to Hospital. These forced placements consume no voluntary movement. Health and Jail remain separate. | Exit destination and movement consumption are open (RULE-004). |
| V1-03 | Captain can enter Command from either A or B, using the normal one movement per round. Election places the winner in Command without consuming that movement. Losing Captain while Healthy returns them to their last A/B room; Jail/injury take their normal destinations. | Captain adjacency/routing is provisional (RULE-005). |
| V1-04 | If no eligible Captain candidate exists, continue without Captain and retry eligibility at the next round boundary. A required runoff repeats among tied candidates. An all-abstain ballot elects nobody and defers to the next round rather than randomly assigning Captain. | The no-candidate/all-abstain fallback has no approved rule. The positive-vote tie/runoff remains as written. |
| V1-05 | Cracker may Rescue a player in Hospital from A/B as an **explicit same-location exception**, without moving or revealing the Cracker role. Otherwise Rescue uses the same-location rule; injured self-Rescue remains allowed. | This is a proposed rule exception, not a reading of canon. Visible Cracker-only Hospital access can identify the secret role. Owner can instead choose explicit Hospital entry with visible role inference and define its entry/exit movement. |
| V1-06 | Validate same-location and Command immunity at registration. Later actor injury/Jail/elimination never cancels a registered action. At resolution, do not recheck actor/target location; do recheck target health and defenses. A target already Eliminated receives no further effect. | Registration-to-resolution location checks are open (RULE-001). This locks a legally registered target without redirecting. |
| V1-07 | Inside the normal action/attack stage, resolve in that round's recorded turn order; for one actor, Main Action before Shot. Network arrival never decides competing-effect order. Then Rescue, Round 3 Supplier, elimination/reveals, victory, Captain flag remain in confirmed order. | Intra-stage order is open (RULE-002). |
| V1-08 | Record the Hacker's one Round 5 Code attempt anytime before normal Round 5 resolution closes; evaluate Code victory with the other victories after normal Round 5 effects. Do not end the match immediately on submission. | Submission is confirmed; terminal checkpoint is open (RULE-007). |
| V1-09 | Captain election/runoff, Jail vote, release vote and showdown target registration each use 60-second server windows. Accept final inputs until the deadline; close at deadline even if everyone responded earlier. Missing ballots abstain; missing special target means no shot. No fabricated votes/targets. | These durations and missing-input rules are not confirmed (RULE-008). Ordinary/Hack durations are already confirmed. |
| V1-10 | All non-eliminated players vote, including Injured/Jailed. Election candidates are Healthy/free. Jail targets are non-eliminated/free. Self-voting is allowed. One final ballot per player per phase; ballot choices stay private until an aggregate tally is published at closure. | Candidate/voter eligibility is partly confirmed; target set, self-votes, ballot replacement and exact ballot disclosure need a decision. |
| V1-11 | At voting start, the Captain may use the single match-wide release request for **one selected jailed player**. Release vote precedes the normal Jail vote; a failed request still consumes the opportunity. Give the Captain a 60-second release-choice window; declining/missing choice proceeds to normal Jail vote without consuming the opportunity. | One use/threshold/order are confirmed; selected-prisoner versus release-all and choice window are not. |
| V1-12 | No automatic pause or forfeit on disconnect. Ordinary/Hack/vote/showdown windows continue on server time; reconnect restores the same identity/seat. Host may explicitly abort an unusable session, producing a recorded Aborted result without a winner. No arbitrary host phase override. | Disconnect/pause/abort is an unconfirmed operating policy (RULE-009). |
| V1-13 | Ordinary shots, Disabler attacks and Hack target another player. Scan, Protection and Rescue retain their explicit self-target exceptions. Limit each own ordinary turn to one role Main Action, one ordinary Shot and one independent Hack request, subject to resources. | Generic quotas and self-targeting are not fully explicit in sources. |
| V1-14 | Hacker Scan consumes that round's Scan at acceptance and immediately returns its authorized private result: failed guess gives no Code information; correct guess gives only membership. It gives no location-independent access to Command targets. | Scan content/one use are confirmed; immediate versus scheduled feedback needs a concrete checkpoint. |
| V1-15 | Reserve Rescue and Disabler uses when their actions are accepted. A valid queued Rescue with no heal at resolution still consumes its use. Undercover can grant to a recipient only once per match; reserve that lifetime receipt at registration so it cannot race. A canceled/non-live target gets no effect and no refund. | Resource consumption for no-effect/canceled actions must be explicit; protection lifetime limit itself is confirmed. |
| V1-16 | Supplier selects two distinct same-location, non-eliminated recipients, without a role-dependent rejection. Officer may receive an unusable extra weapon, but never gets a second ordinary shot. Supplier's successful grants are disclosed only to each recipient and Supplier; no public weapon marker. | Supplier→Officer eligibility/representation and recipient disclosure are open (BAL-005, RULE-003). |
| V1-17 | Protection grant/activation/consumption is known only to Undercover, and never shown to the recipient or public. The attacker sees registration and later completion only, without a block/cause explanation. Public health/location changes are neutral facts. | Protection/result audiences need owner approval (RULE-003). This proposal favors secret defense. |
| V1-18 | Faction reveal happens at the next public phase after the attack stage, before the next voting/turn/showdown phase; exact roles and Code are disclosed only at match end. A terminal result counts as that public phase. | Broad faction timing and role secrecy are confirmed; the full phase-specific reveal checkpoint and Code end disclosure need precision. |
| V1-19 | Alien's simultaneous-elimination condition means both actual factions go from having a surviving member to having none during the same complete resolution stage/checkpoint. Recheck victories only after the full registered stage, including all showdown shots; do not stop on an intermediate shot. | The word simultaneously is not defined for ordered damage. |
| V1-20 | Showdown special shots consume once at registration, resolve in Round 5 order even if their shooters later die, and do nothing if their fixed target is already Eliminated. No target redirect and no refund. | The main showdown rule is confirmed; missing/non-live target handling must be explicit. |
| V1-21 | Use real Firebase connectivity for V1. Persistent offline gameplay is disabled. Seat recovery may move a seat to a new authenticated identity through a one-time code explicitly authorized by the owner/host; the old identity loses access atomically. Recovery never re-deals roles or resets resources. | In-person does not imply offline. Recovery operating policy and who may issue a transfer need owner confirmation; technical identity controls are implementation work. |

## Review and implementation boundary

The approved set includes game-rule choices and an explicit Rescue exception (V1-05). Future changes require a new owner decision, tests and immutable version pin. The full-game engine implements this profile with optional powers off. The historical Officer fixture retains its original protocol and source pin.

Frontend and Game Balance still review shared protocol/view adoption. Completing server implementation does not prove real-device integration, human balance, cloud task/IAM delivery or a deployed V1 release.
