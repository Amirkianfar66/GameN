Development only. These controls stand in for the backend's own scheduler and exist nowhere in the game client. They replay authored views and events in a fixed order; they do not resolve anything.

Script

Both variants send identical views to every audience. They differ only in truth that stays on the server side of this harness.

Commands

The command desk follows the command contract as stated for protocol 1 and applies no game rule; it never judges a target. An arrangement below applies to the next command request only, then the desk answers as scripted again.

A request that gets “no answer” here fails at once with an empty gateway error; a real one could also hang until the client gives up. The feeds keep running, so a screen stays live while its command goes unanswered.

Presentation events

Each audience has an event stream of its own, written together with its views and kept, so a screen that reconnects is handed all of it again. A registration puts one event on the registering seat’s stream and nothing anywhere else. The two facts below are frontend-authored and synthetic: they follow no rule and are the outcome of nothing.
